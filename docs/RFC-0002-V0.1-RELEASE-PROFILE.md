# RFC-0002: v0.1 Release Profile

- **Status:** Draft; implementation is partially aligned
- **Authors:** MCP State Twin maintainers
- **Created:** 2026-08-17
- **Target:** first tagged `v0.1.0`
- **Depends on:** RFC-0001, SPEC-0001 through SPEC-0006, and accepted ADRs

## 1. Purpose

RFC-0001 defines the product and long-term architecture. This RFC defines the
smaller, testable contract that a build must satisfy before maintainers may tag
it `v0.1.0`.

SPEC-0001 defines the TwinSpec core, SPEC-0002 runtime semantics, SPEC-0003
MCP/security boundaries, and SPEC-0004 evidence and release rules. This file
selects the supported subset; it does not turn roadmap components into
implemented features.

SPEC-0005 defines the bounded scripted scenario and evidence-report contract.
SPEC-0006 separates runtime correctness, protocol compatibility, and model
evaluation, and defines the evidence required for host-specific claims.

The development preview also contains the accepted ADR-0011 storage/clock
extension. It is not a claim that scheduler, entropy, or fault profiles are
part of the stable v0.1 release.

The keywords **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are
normative as described by RFC 2119 and RFC 8174 when written in capitals.

This document is intentionally stricter than a roadmap. A capability is not
part of the release merely because its type or endpoint exists. Each normative
claim needs an executable test, an architectural proof, or an explicit
unsupported result.

## 2. Release labels

| Label | Meaning |
|---|---|
| development preview | Untagged code; APIs and storage may still change |
| `v0.1.0-alpha.N` | Integrator preview; known release gates may remain open |
| `v0.1.0` | Every required gate in section 15 is satisfied |

The repository MUST NOT use the plain `v0.1.0` tag while a required gate is
open. Passing unit tests alone is not sufficient.

## 3. Supported profile

The first release profile is deliberately narrow:

- one local runtime process;
- one TwinSpec and one SQLite database per process;
- MCP tools over stateless Streamable HTTP;
- a separately bound HTTP control plane;
- local or CI execution with synthetic fixtures;
- deterministic serial state transitions;
- logical immutable snapshots and isolated branches;
- declarative CEL expressions;
- JSON Schema 2020-12 tool input and output contracts.

The following are outside the `v0.1.0` support claim:

- production passthrough of any kind;
- cloud multi-tenancy;
- native code extensions in TwinSpec;
- automatic fidelity promotion;
- distributed transactions;
- deterministic multi-agent interleaving;
- virtual-time advancement, scheduled faults, or eventual consistency;
- arbitrary remote JSON Schema references;
- L2/L3 fidelity for the bundled issue-tracker twin.

Unsupported behavior MUST fail explicitly. It MUST NOT silently use a live
service or manufacture a plausible result.

The private control-plane clock endpoint is implemented as a preview extension,
but remains outside the stable support claim until scheduler semantics and
recovery evidence are complete.

### 3.1 Scope-change proposal relative to RFC-0001

RFC-0001 currently says v0.1 completes both L0 cassette replay and L1 stateful
runtime. This RFC proposes narrowing the first stable release to the L1 runtime
and deferring recorder/L0 until redaction, consent, and incomplete-trace
semantics are independently ready. The reason is risk containment: an unused
recorder should not be rushed into a hermetic runtime merely to satisfy a broad
milestone.

This proposal is **not effective while RFC-0002 is Draft**. Until maintainers
accept it and amend RFC-0001, recorder/L0 remains an open RFC-0001 release gate.

## 4. Environment identity

An evaluation environment is identified by:

```text
EnvironmentID = (
  runtime semantic version,
  TwinSpec digest,
  snapshot state digest,
  virtual clock,
  ordered tool calls
)
```

For a fixed supported runtime build and identical EnvironmentID inputs, the
runtime MUST produce identical structured results, domain error classes, state
digests, and terminal state.

Wall-clock timestamps used for operational audit are not part of simulated
state and are excluded from deterministic equality. They MUST NOT be visible to
TwinSpec expressions.

## 5. TwinSpec admission

Before a server starts, it MUST:

1. reject TwinSpec documents larger than 1 MiB, decode exactly one YAML
   document, and reject unknown top-level or typed fields;
2. require `statetwin.dev/v1alpha1` and `kind: Twin`;
3. validate names, fidelity metadata, upstream binding state, entities, tools,
   effects, queries, and invariants;
4. compile every CEL expression;
5. compile every tool input/output JSON Schema;
6. calculate the canonical TwinSpec and MCP tool-surface digests;
7. enforce ADR-0008 upstream binding semantics;
8. refuse startup if any step fails.

TwinSpec expressions MUST use the bounded CEL environment from ADR-0003. Tool
arguments are values only and MUST never be reinterpreted as CEL source. Each
expression is limited to 4,096 UTF-8 bytes and each evaluation uses a CEL cost
limit of 10,000.

## 6. JSON Schema contract

Tool schemas use JSON Schema Draft 2020-12. If `$schema` is absent, the runtime
MUST use Draft 2020-12.

The runtime MUST:

- compile schemas once during runtime construction;
- assert registered `format` constraints;
- validate the complete input before any effect;
- validate the complete successful output before commit;
- return `INVALID_INPUT` for input validation failures;
- return `INTERNAL_TWIN_ERROR` and roll back for declared output mismatches;

The admission and result budgets are:

| Limit | Default |
|---|---:|
| TwinSpec document | 1 MiB |
| entity count | 256 |
| tool count | 256 |
| invariant count | 512 |
| schema canonical bytes | 256 KiB |
| schema nesting depth | 32 |
| tool result canonical bytes | 1 MiB |
| Scenario document | 256 KiB |
| Scenario steps | 256 |
| Scenario assertions | 1,024 |
| YAML document depth | 128 |
| Scenario JSON value depth | 64 |
| Scenario trace canonical bytes | 16 MiB |

These are resource-safety limits, not a claim that arbitrary large production
payloads are faithfully simulated.
- preserve the same schema in MCP `tools/list`;
- reject a schema that requires an external resource load.

Local fragments and `$defs` MAY be used. Network or filesystem `$ref` loading
is outside `v0.1.0` because it would break hermetic startup and introduce a
supply-chain input.

Validation errors SHOULD contain an instance location but MUST NOT include
credentials, request headers, or Go runtime internals.

## 7. State transaction

A normal tool call is one serial SQLite transaction:

```text
read branch head
  -> verify TwinSpec digest binding
  -> clone working state
  -> validate input
  -> evaluate preconditions
  -> apply deterministic effects
  -> execute declared query
  -> evaluate postconditions and global invariants
  -> build and validate output
  -> atomically commit state head and tool audit
```

A domain failure MUST:

- preserve the previous state digest;
- increment the branch call count;
- append a tool-call audit record;
- return a typed error payload.

An internal evaluator, storage, or schema error MUST NOT be rendered as a
successful domain result.

## 8. Snapshot and branch contract

Snapshots are immutable logical copies. Their identity MUST bind at least:

- snapshot name;
- TwinSpec digest;
- state digest;
- virtual clock.

Every fork MUST copy the snapshot state into a new branch namespace. A model
MUST NOT select or override its branch through tool input; the harness binds
the branch in the MCP URL.

Reset MUST restore state, TwinSpec binding, and virtual clock from the selected
snapshot and reset the branch call count. Reset MUST NOT delete historical
audit entries. A later tool call with a reused logical call index MUST remain
valid.

## 9. SQLite file contract

The runtime MUST set and verify:

- SQLite `application_id = 0x5354574E` (`STWN`);
- SQLite `user_version` equal to the implemented schema version.

It MUST reject:

- a non-zero foreign `application_id`;
- a schema version newer than the runtime understands;
- a migration that cannot commit atomically.

Schema migration MUST preserve committed state and audit history. Release
builds MUST have a migration test for every previously tagged database schema.
The current development migration also removes the obsolete unique constraint
on `(branch_id, call_index)`.

## 10. Data-plane contract

The agent-facing endpoint is `/mcp/{branch}`. `{branch}` MUST match:

```regex
^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$
```

The data plane MUST expose only TwinSpec business tools. Snapshot, fork, reset,
state inspection, diff, assertions, expected results, and fault controls MUST
NOT appear in `tools/list`.

The server implementation name MUST contain `SIMULATED/`. MCP annotations are
informational hints only and MUST NOT be treated as authorization.

The runtime MUST use one bounded server/tool registry rather than caching an
unbounded server instance for arbitrary branch paths. Branch routing MUST be
carried in trusted request context, not model-visible arguments.

## 11. Control-plane contract

The control plane MUST:

- bind separately from the MCP data plane;
- require a non-empty bearer token;
- accept only an `Authorization: Bearer <token>` scheme;
- compare the token in constant time after structural parsing;
- reject unknown JSON fields and bodies larger than 1 MiB;
- set `Cache-Control: no-store`;
- never log or persist the bearer token.

Snapshot, fork, and reset MUST append a control audit record in the same
transaction as the mutation. The minimum control audit fields are operation,
branch, snapshot, before digest, after digest, and operational timestamp.

The development bearer token is not a remote security architecture. Until TLS,
network policy, principal identity, and authorization are implemented, both
planes SHOULD remain on loopback.

## 12. HTTP resource limits

The default server profile uses:

| Limit | Default |
|---|---:|
| request body | 1 MiB |
| maximum headers | 1 MiB |
| read-header timeout | 5 s |
| read timeout | 30 s |
| write timeout | 30 s |
| idle timeout | 60 s |

Changes to these defaults require tests and documentation. These limits are
process-safety controls, not multi-tenant quotas.

## 13. Error taxonomy

The stable `v0.1` classes are:

| Class | Meaning | State commit |
|---|---|---|
| `INVALID_INPUT` | tool input violates declared schema | no |
| `PRECONDITION_FAILED` | generic declared precondition failed | no |
| `NOT_FOUND` | modeled entity is absent | no |
| `CONFLICT` | modeled state conflicts with requested transition | no |
| `INVARIANT_VIOLATION` | postcondition/global invariant rejected working state | no |
| `UNMODELED_BEHAVIOR` | tool or effect is explicitly not modeled | no |
| `INTERNAL_TWIN_ERROR` | TwinSpec/runtime contract error | no |

Unknown errors MUST NOT be converted to success. Future fault classes require
an ADR because timeout-before-effect and timeout-after-effect have different
retry semantics.

## 14. Security and privacy requirements

For `v0.1.0`:

- no upstream connector or passthrough path may exist in hermetic mode;
- fixtures and examples MUST be synthetic;
- tool and control audit MUST NOT contain HTTP authorization headers;
- external TwinSpec code execution is forbidden;
- remote schemas are forbidden;
- the data plane MUST reject invalid branch identifiers;
- release tests MUST prove that control tools are undiscoverable over MCP;
- documentation MUST warn that the data plane has no production auth/TLS.

Recorder-specific secret redaction remains a release blocker if recorder code
enters `v0.1.0`. If recorder is deferred, the codebase MUST contain no recorder
or upstream network path and the release notes MUST say so.

## 15. Required release gates

| Gate | Required evidence | Current development state |
|---|---|---|
| deterministic kernel | 1,000-call equal-digest replay | passing |
| schema admission | strict YAML, CEL, input/output JSON Schema tests | passing |
| state atomicity | failed input/output/invariant rollback tests | passing |
| snapshot isolation | immutable base and 100 concurrent isolated forks | passing |
| storage compatibility | identity/version/refusal/migration tests | partial |
| control isolation | `tools/list` negative test and URL-only branch binding | passing |
| control audit | atomic snapshot/fork/reset audit tests | passing |
| HTTP bounds | auth grammar, body-limit, timeout configuration tests | partial |
| MCP conformance | official `v0.1.16`: initialize, ping, tools-list, JSON Schema 2020-12 | passing on Linux CI |
| hermeticity | only-loopback Linux namespace job; CI run #6 | passing |
| provider smoke | documented OpenAI-family and Anthropic-family runs | open |
| drift handling | canonical local tool-surface fingerprint and fail-closed binding tests | passing; upstream inspector remains outside current scope |
| recorder/L0 scope | accept section 3.1 or implement recorder redaction gates | open |
| second reference domain | independent state model and scenarios | open |
| P0 traceability | every P0 mapped to test, proof, or excluded code path | partial |
| documentation integrity | README/status matrix match executable evidence | passing |

An `open` required gate prevents `v0.1.0`. Maintainers MAY publish an alpha if
the open gates are listed prominently.

## 16. MCP conformance policy

The official MCP conformance framework is currently documented by its own
maintainers as unstable. CI integration MUST therefore:

- pin an exact conformance release;
- list the exact server scenarios or suite used;
- store any expected-failure baseline in the repository;
- fail on new failures and stale expected failures;
- avoid claiming conformance outside the tested tools-first subset.

SDK unit tests are necessary but do not replace protocol conformance tests.

## 17. Change control

The following require an ADR and compatibility note:

- canonical JSON changes;
- CEL environment or cost-limit changes;
- SQLite schema changes;
- snapshot identity changes;
- error-class semantic changes;
- enabling remote schema resolution;
- adding any upstream connector;
- moving a control function into the MCP surface;
- changing deterministic scheduling.

Every incident or correctness bug SHOULD produce a regression test before the
fix is considered complete.

## 19. Acceptance

This RFC may move from Draft to Accepted only after:

1. maintainers review every required gate;
2. RFC-0001 conflicts are reconciled explicitly;
3. Implementation Status links each passing gate to tests;
4. the CI conformance and egress-deny strategy is proven;
5. no README claim exceeds this profile.
