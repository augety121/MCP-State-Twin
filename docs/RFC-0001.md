# RFC-0001: MCP State Twin — Stateful Service Virtualization for Agent Tools

- **Status:** Draft umbrella RFC; v0.1 normative details are delegated to SPEC-0001 through SPEC-0006 and RFC-0002
- **Date:** 2026-08-17
- **Decision owner:** Project maintainers
- **Canonical language:** English identifiers and protocol names; explanatory text in Chinese
- **Target release:** v0.1 design freeze
- **Scope:** Tools-first MCP stateful twin runtime
- **Review rule:** 任何破坏本文 Hard Invariants 的实现变更都必须走新的 RFC/ADR，而不能作为普通重构合入。

## Normative hierarchy

This RFC defines product boundary and long-term architecture. The executable
v0.1 contract is defined by RFC-0002 and SPEC-0001 through SPEC-0006. The
vNext proposals SPEC-0007 and SPEC-0012 are adopted only for their bounded
preview subsets documented by ADR-0011. If a
long-term component in this document conflicts with the release profile, the
release profile wins for v0.1 and the component remains a roadmap item.

## 0. Executive decision

本项目暂定名 **MCP State Twin**（品牌名发布前再做商标和 GitHub/npm/PyPI 冲突检查）。

项目定位不是 Agent Framework、Memory、RAG、Workflow Engine、MCP Gateway、Mock Server，也不是通用 Digital Twin 平台。

**一句话定义：**

> MCP State Twin is an open-source, deterministic, forkable stateful service-virtualization runtime that exposes the same agent-facing MCP tool surface as a real service, while executing against an isolated simulated state instead of the production system of record.

它解决一个明确的工程问题：

> Agent eval、训练、回归、模型升级、故障注入和多方案对比，需要真实的“有状态外部世界”；直接调用生产/测试 SaaS 会产生副作用、成本、速率限制、数据污染与不可复现性，而传统 fixture/VCR 只能重放已见过的请求，无法可靠支持新的、分叉的多步工具轨迹。

核心产品原语：

```text
Real MCP Server
      |
      | record / inspect contracts
      v
+------------------+
| Trace + Contract |
+---------+--------+
          |
          | assisted compile + human validation
          v
+------------------+
|    TwinSpec      |
| entities         |
| transitions      |
| invariants       |
| error models     |
+---------+--------+
          |
          v
+------------------------------------------------+
| MCP State Twin Runtime                         |
| snapshot | fork | virtual clock | seeded chaos |
| transactional transition engine | state diff   |
+----------------------+-------------------------+
                       |
                       | same agent-facing tools
                       v
       ChatGPT / Claude / Codex / custom agents
```

## 1. Why this project and why not the rejected alternatives

截至 2026-08-17，我们对以下方向做过精确竞品检查并主动否决：generic durable agent runtime、prospective memory runtime、portable agent checkpoint、transactional effect runtime、agent action receipts、tool semantic IR/compiler、agent context build system、MCP behavioral regression framework、agent dependency lockfile/SBOM。它们均已有强近邻或成熟 owner。

MCP State Twin 保留下来的原因不是“绝对没人做”，而是存在可验证的工程缝隙：

1. **Record/replay** 项目能固定历史交互，但对“agent 走了新的合法轨迹”支持有限。
2. **Mock server** 能返回假数据，但通常没有显式、可审计的领域状态转移和不变量。
3. **Agent benchmarks** 已证明 stateful、interdependent、seeded environments 很重要，但大多为 benchmark 手工构造环境，而不是一个把真实工具系统转成可复用 twin 的基础设施。
4. **Domain digital twins** 能高保真模拟一个领域，但不是通用 agent-tool service virtualization 层。
5. 传统 enterprise service virtualization 已长期存在，但 Agent/MCP 需要额外处理 model-facing tool descriptions、multi-turn tool trajectories、virtual time、branch/fork、agent-safe control plane isolation 等问题。

因此本项目不宣称“first digital twin”或“first stateful MCP sandbox”。我们的差异化声明必须限定为：

> **A general-purpose MCP-compatible, forkable stateful service-virtualization runtime with an explicit machine-reviewable transition contract (TwinSpec), designed for agent evaluation and training.**

## 2. Goals

长期架构目标（不是当前 v0.1 实现承诺）：

- 对目标 MCP server 的 **tool surface** 进行捕获、版本指纹和兼容暴露。
- 用显式 `TwinSpec` 表达 entities、state、preconditions、effects、postconditions、errors、virtual time 与 seeded nondeterminism。
- 在 hermetic 模式下保证 **zero production writes by construction**。
- 给定相同 runtime version、snapshot、seed 和 tool-call sequence，产生确定性一致的 twin state 与 tool results。
- 支持 snapshot、fork、reset、export、import、canonical state diff。
- 支持 scenario runner，使不同模型在同一初始世界状态上比较。
- 将 control plane 与 agent-visible MCP data plane 强隔离。
- 提供 trace-assisted TwinSpec bootstrap，但任何自动推断 MUST 被标记为 `unverified`，不能伪装成真实服务语义。
- 支持至少 OpenAI/ChatGPT 与 Anthropic/Claude 可消费的远程 MCP tool surface；core 不依赖具体模型 SDK。
- 具备 CI-friendly、local-first、single-binary 优先的开发体验。

## 3. Non-goals

v0.x 明确不做：

- 不做通用 Agent orchestration / planning / memory / RAG。
- 不模拟模型本身；环境确定性不代表 LLM 确定性。
- 不保证自动从任意黑盒服务“准确推断全部业务规则”。这是不可证明也不可工程保证的。
- 不保证 twin 与真实服务在所有隐式行为上 observationally equivalent。
- 不把 LLM judge 作为状态正确性的最终 oracle。
- 不在 v0.1 代理真实生产写操作。
- 不把 snapshot/fork 能力暴露给被测 Agent，除非 scenario 明确授权。
- 不在 v0.1 建 SaaS 控制台、多租户云托管、商业 registry。
- 不替代 MCP 官方 conformance suite。
- 不替代 WireMock/LocalStack 等一般 API 测试工具；只有 agent-facing stateful semantics 是本项目重点。

## 4. Design principles

### 4.1 Deterministic core, probabilistic edge

LLM 可以用于**帮助生成** TwinSpec 草稿、解释 trace 或建议映射，但状态机执行、约束校验、snapshot、fork、diff、fault schedule MUST 是确定性代码。

### 4.2 Explicit beats inferred

隐式推断出的行为一律低信任。生产可用 TwinSpec 必须能由人 review、能被测试、能被版本控制。

### 4.3 Hermetic by default

`statetwin serve` 默认不得访问 upstream production service。任何 passthrough 都必须显式启用、按 tool allowlist、按 method 分类，并在 CI 模式禁用 write passthrough。

### 4.4 Same surface, different world

被测 Agent 应看到与真实 MCP server 尽可能一致的 tool name、description、input schema、output schema 和错误结构；仿真控制接口走独立 control plane，避免 prompt/tool-selection 被测试框架污染。

### 4.5 State is the oracle

最终 eval 应优先比较 terminal state / invariants / postconditions，而不是比较 Agent 的自然语言答案。

### 4.6 Fidelity is declared, never implied

每个 Twin MUST 声明 fidelity level、未建模字段、未知 side effects 与 last validated upstream fingerprint。系统不得将 L0/L1 twin 显示为 production-equivalent。

## 5. Hard invariants

以下是不允许被普通实现选择破坏的约束。

**I-1: No hidden live writes.** Hermetic mode 下 runtime MUST NOT 发起到真实 upstream 的写请求。网络层应可通过 sandbox/egress deny 做第二层验证。

**I-2: Control plane isolation.** snapshot/fork/reset/inject-fault/import 等工具 MUST NOT 出现在默认 agent-facing `tools/list`。

**I-3: Deterministic transition.** 对相同 `(runtime_version, TwinSpec_digest, snapshot_digest, seed, ordered_calls)`，状态哈希与结构化 tool results MUST 一致；时间戳、UUID 等必须来自 deterministic providers。

**I-4: Explicit unknown.** 无法模拟的行为 MUST 返回 typed `UNMODELED_BEHAVIOR` / `UNSUPPORTED_EFFECT`，不能编造一个“看起来合理”的成功结果。

**I-5: Version binding.** TwinSpec MUST 绑定 upstream tool-surface fingerprint；发现 schema/description/toolset 漂移时默认 fail validation，而不是静默继续。

**I-6: Atomic single-tool transition.** 单个 twin tool call 对模拟 state 的修改 MUST 原子提交；失败时不能留下半提交状态，除非 TwinSpec 明确模拟 `partial_effect`。

**I-7: Test-state ownership.** 每个 scenario/run MUST 有独立 branch/snapshot namespace，避免并行 eval 互相污染。

**I-8: No model as correctness oracle.** deterministic contract validation 和 state assertions 不得依赖模型判断。

**I-9: Secrets stay out of artifacts.** raw authorization headers、API keys、OAuth tokens MUST 不进入 TwinSpec、committed traces 或 state exports。

**I-10: Evidence-preserving errors.** runtime 不应把 unknown/timeout/validation error 自动改写成 success；错误分类必须可审计。

## 6. Fidelity model

Twin fidelity 是产品的一等概念。

### L0 — Cassette Replay

- 精确或规则化匹配已记录请求。
- 适合 deterministic smoke tests。
- 不支持真正的新状态轨迹。
- 不得用于声称“业务逻辑等价”。

### L1 — Stateful Template Twin

- 有 entities 与 CRUD-like 状态转移。
- 从 schema、trace、fixture 辅助生成。
- 常见流程可走新轨迹。
- 隐式业务规则覆盖不完整。

### L2 — Contract-Backed Twin

- 关键 transitions、preconditions、postconditions、invariants 均人工审阅并有 golden differential tests。
- 可以作为正式 agent eval 环境。
- 仍需列出未建模区域。

### L3 — Native/Reference Twin

- 使用领域方提供的 reference logic 或共享核心库模拟关键行为。
- 可有明确误差界或一致性声明。
- 适合训练、强化学习、强回归。

v0.1 目标：L0 + L1 runtime 完整，支持构建 L2；不承诺通用 L3。

## 7. TwinSpec

TwinSpec 是版本化、可 diff、可 review 的核心 IR。建议 YAML authoring + canonical JSON hashing。

```yaml
apiVersion: statetwin.dev/v1alpha1
kind: Twin
metadata:
  name: github-lite
  upstream:
    protocol: mcp
    surfaceDigest: sha256:...
  fidelity:
    level: L2
    validatedAt: 2026-08-17T00:00:00Z

clock:
  mode: virtual
  initial: 2026-08-01T00:00:00Z

state:
  entities:
    repository:
      key: [owner, name]
      schema: {...}
    issue:
      key: [repo, number]
      schema: {...}
      indexes: [repo, state]

invariants:
  - id: issue-number-positive
    assert: issue.number > 0

faultModels:
  rate_limit:
    type: scheduled

 tools:
  - name: create_issue
    inputSchema: {...}
    reads:
      - repository($input.owner, $input.repo)
    preconditions:
      - repository.exists == true
    effects:
      - insert issue(...)
    result:
      template: {...}
    errors:
      - when: repository.exists == false
        code: NOT_FOUND
```

### 7.1 Required tool semantics

每个 stateful tool 至少要能声明：

- `reads`: 可能读取的模拟资源。
- `writes`: 可能修改的模拟资源。
- `preconditions`: 调用前条件。
- `effects`: 状态转移。
- `postconditions`: 提交后必须满足的条件。
- `result`: 结构化输出构造。
- `errors`: 可模拟错误与触发条件。
- `timeEffects`: 是否推进 virtual clock、延迟可见性等。
- `idempotency`: 是否按 key 去重。

### 7.2 Expression language

v0.1 MUST 不实现任意脚本执行。表达式语言应是受限 DSL：比较、布尔、集合查询、字段映射、有限算术、引用当前 state/input/clock。原因：

- 可审计。
- 可静态分析读写集。
- 可 deterministic evaluate。
- 减少 TwinSpec 供应链 RCE 风险。

复杂逻辑通过 signed/native adapter 扩展，并明确从 declarative spec 升级为 executable code trust level。

## 8. Architecture

```text
                    +------------------------+
                    | Upstream MCP Server    |
                    +-----------+------------+
                                |
                        Recorder / Inspector
                                |
                  +-------------v--------------+
                  | Trace Store + Surface Snap |
                  +-------------+--------------+
                                |
                   bootstrap / validate / diff
                                |
                        +-------v-------+
                        | Twin Compiler |
                        +-------+-------+
                                |
                          TwinSpec bundle
                                |
         +----------------------v----------------------+
         |              State Twin Runtime             |
         |                                              |
         | MCP Data Plane | Transition Engine | Clock  |
         | State Store    | Snapshot/Fork     | Chaos  |
         | Assertion Eval | State Diff        | Audit  |
         +-----------+---------------------+------------+
                     |                     |
             agent-visible MCP        private control API
                     |                     |
       +-------------+-----------+   CLI / CI / eval runner
       |             |           |
    ChatGPT        Claude      custom agents
```

### 8.1 Components

**Surface Inspector**

- Captures `tools/list` and supported metadata.
- Produces canonical `surfaceDigest`.
- Detects descriptor/schema drift.

**Recorder**

- Optional transparent proxy for selected upstream calls.
- Redacts secrets before persistence.
- Stores input/output/error/timing metadata.
- Recording is evidence, not truth.

**Twin Compiler**

- Imports tool schemas + traces + optional OpenAPI/domain fixtures.
- Generates a draft TwinSpec.
- LLM assist MAY be used behind a flag, but output remains `unverified`.

**Transition Engine**

- Evaluates preconditions.
- Applies state changes inside one DB transaction.
- Evaluates postconditions and global invariants before commit.
- Produces structured result/error.

**State Store**

- v0.1: SQLite-backed transactional state and metadata.
- Snapshot strategy: logical checkpoint + copy-on-write/delta layers where useful.
- Exports canonical JSON for portability; internal DB layout is not public API.

**Virtual Clock**

- Wall-clock isolation.
- `now()` comes from scenario clock.
- Supports explicit advance and scheduled delayed effects.

**Chaos Engine**

- Seeded deterministic faults only.
- Latency, timeout-before-effect, timeout-after-effect, rate limit, stale visibility, partial effect are separate fault classes.

**Scenario Runner**

- Creates branch from known snapshot.
- Runs one or more external agents against twin endpoint.
- Evaluates terminal state assertions.
- Produces state diff + tool trace + environment digest.

## 9. Data plane vs control plane

### 9.1 Agent data plane

Default MCP endpoint exposes only the copied/simulated business tools.

Example:

```text
POST /mcp
  tools/list -> [search_issues, create_issue, add_comment]
  tools/call -> simulated result
```

### 9.2 Control plane

Private endpoint / CLI provides:

- create/list/delete snapshots
- fork branch
- reset branch
- advance virtual clock
- install fault schedule
- inspect canonical state
- diff branches
- validate TwinSpec
- import/export fixtures

Control plane MUST bind to loopback/private socket by default and MUST use separate auth if remotely exposed.

## 10. State and transaction semantics

### 10.1 Single-call atomicity

默认每个 tool call 是一个 state transaction：

```text
load branch head
 -> validate input
 -> read state
 -> preconditions
 -> compute effects
 -> postconditions + invariants
 -> commit
 -> render result
```

如果 TwinSpec 故意模拟 non-atomic backend，可定义 `partial_effect` fault，但它必须显式、可重复、可观察。

### 10.2 Concurrency

v0.1 正常模式采用确定性串行调度，原因是 agent eval 首先要求可复现。

多 Agent contention 测试放到 v0.2+，通过显式 scheduler policy 选择：

- serialized
- deterministic interleaving
- scripted races

不得把宿主 OS 调度顺序当 benchmark 语义。

### 10.3 Idempotency

TwinSpec 可声明 idempotency key。Runtime 需维护 dedupe ledger，以模拟 downstream 服务的幂等语义。未声明时不能自动假设幂等。

### 10.4 Eventual consistency

通过 `pending effects + virtual clock` 模拟：write 已接受但 read 在 delay 后才可见。所有 delay 基于 virtual time，而不是 `sleep()`。

## 11. Snapshot and fork semantics

Snapshot 是 immutable logical state root：

```text
snapshot S0
  |-- fork A -> calls -> state A3
  |-- fork B -> calls -> state B7
  `-- fork C -> fault schedule -> state C4
```

要求：

- Snapshot ID 由 canonical state + TwinSpec digest + runtime schema version 派生/绑定。
- Fork 不得修改父 snapshot。
- Branch 可产生 child snapshot。
- Diff 必须 canonical、stable、machine-readable。
- GC 只能删除不可达的 internal deltas，不能改变已有 export digest。

## 12. Determinism contract

环境确定性定义为：

```text
E = (runtime_version,
     twinspec_digest,
     snapshot_digest,
     scenario_seed,
     ordered_tool_calls)

execute(E) -> (ordered_results, final_state_digest)
```

在相同受支持平台/版本下，结果 MUST 可复现。

所有 nondeterministic primitives 都必须被虚拟化：

- current time
- UUID/random IDs
- random sampling
- fault schedule
- pagination cursor generation
- async completion ordering（支持后）

不包含 LLM 生成本身。要比较模型，runner 允许 N 次 trials；世界状态每次从同一 snapshot 重置。

## 13. Upstream capture and drift

### 13.1 Surface fingerprint

Fingerprint 至少包含规范化后的：

- tool names
- descriptions
- input schema
- output schema（若有）
- annotations/security metadata（若可见）
- server instructions that influence agent use（若协议表面提供）

description 变化被视为潜在 agent behavior change，不能只比较 JSON schema。

### 13.2 Drift states

Twin 与 upstream 关系：

- `CURRENT`: fingerprint 匹配最后验证版本。
- `DRIFTED`: tool surface 已变化。
- `UNKNOWN`: 无法访问 upstream 验证。
- `UNBOUND`: spec 从未绑定 upstream。

CI 用的 L2 twin 在 `DRIFTED` 状态默认 fail closed。

## 14. Trace-assisted model extraction

自动生成是 bootstrap，不是 oracle。

Pipeline：

```text
schemas + recorded traces
 -> entity/key candidates
 -> read/write dependency candidates
 -> transition candidates
 -> inferred invariants
 -> DRAFT TwinSpec
 -> human review
 -> differential tests
 -> VERIFIED TwinSpec
```

### 14.1 What can be inferred safely-ish

- 字段形状、enum、常见 entity IDs。
- obvious CRUD relation。
- observed error envelope。
- observed correlation between input and output。

### 14.2 What cannot be assumed

- 未出现过的业务规则。
- 权限模型完整性。
- hidden side effects。
- fraud/risk engines。
- eventual consistency bounds。
- payment semantics。
- cross-service distributed transactions。

系统必须在 UI/CLI 中把 observed、inferred、declared、verified 四种 provenance 分开。

## 15. Compatibility strategy

### 15.1 MCP first

Core 只实现 MCP server/client semantics，不耦合 OpenAI 或 Anthropic SDK。

当前设计基线：MCP 2026-07-28，优先使用官方 Tier-1 Go SDK，避免手写 JSON-RPC wire protocol。

### 15.2 ChatGPT/OpenAI

ChatGPT Developer Mode 当前支持远程 MCP 的 read/write tools。Twin 只需要作为正常 remote MCP server 暴露模拟工具即可；**不保证 ChatGPT 与其他宿主做出相同 tool-selection 决策**。

OpenAI API 使用 MCP tool 的集成测试放 provider test suite，不进入 state core。

### 15.3 Claude/Anthropic

Claude Messages API 的 MCP connector 当前可连接 remote MCP server，但其公开 connector 功能子集以 tools 为主；因此 v0.1 选择 tools-first 是跨 OpenAI/Anthropic 的最低共同能力。

Claude Code/local clients 可通过标准 MCP transport 接入。

### 15.4 Other hosts

任何遵守兼容 MCP tool subset 的 host 均可接入。我们只承诺协议兼容，不承诺模型行为等价。

## 16. Security model

### Trust zones

1. **Untrusted agent/model** — 可能调用任意可见 tool、构造恶意参数。
2. **Twin data plane** — 处理模拟业务调用。
3. **Control plane** — 高权限，能重置世界、注入故障、读取完整 state。
4. **Upstream recorder** — 可接触真实数据，风险最高。
5. **Artifact store** — traces/spec/snapshots，可能包含敏感业务结构。

### Primary threats

- Agent 发现并调用 control tools 篡改 benchmark。
- Prompt injection 诱导 recorder 泄露 secret。
- Trace 中包含 PII/token 后被提交 Git。
- TwinSpec 可执行扩展导致 RCE。
- Passthrough 误配置导致真实写操作。
- 多租户 branch 越权读取。
- Snapshot export 泄露生产数据。
- Tool description drift 造成错误测试结论。
- Malicious TwinSpec 造成资源耗尽（无限集合、巨大递归）。

### Required controls

- 数据面/控制面端口与 auth 分离。
- Hermetic mode 默认 deny network egress。
- Recorder header/body field redaction policy。
- Secret scanner before trace persistence/export。
- Declarative DSL resource limits。
- Native adapter allowlist + signed checksum policy。
- Per-run namespace ACL。
- Size/time/call limits。
- Audit every control-plane mutation。

## 17. Privacy and data retention

默认开发模式 SHOULD 使用 synthetic fixtures，而不是 production recordings。

若开启 recorder：

- Authorization/Cookie 等标准敏感 headers 必须强制删除。
- 用户可配置 JSONPath/regex/field-class redaction。
- Raw recordings 默认 `.gitignore`。
- Export 前执行 secret scan。
- Snapshot retention configurable；CI ephemeral branch 默认 job 完成后删除。
- 不做“不可逆匿名化”承诺；结构化业务数据可能被重新识别，文档必须明确。

## 18. Observability

每个 run 产出：

- environment digest
- TwinSpec digest
- snapshot digest
- seed
- protocol version
- tool-call trace（不含 secret）
- state mutations
- final state digest
- invariant violations
- fault injections actually fired
- runtime version/build commit

OpenTelemetry integration 是 SHOULD，不是 v0.1 block。

## 19. SLO/SLO-like engineering targets

以下都是 **release targets，不是当前实测声明**：

- Hermetic write egress violations: **0**。
- Same-input environment replay determinism: **100%** on supported platform matrix。
- Relevant MCP conformance tests: **100% pass** before release。
- Transition engine local overhead target: p50 < 5 ms, p99 < 25 ms for small-state tools（不含 model/network）。
- Snapshot/fork target: p95 < 100 ms for a 10 MB logical state on reference CI machine。
- Crash recovery: committed tool call must either be fully visible or absent, never half-applied in normal atomic mode。
- Corrupt state detected by invariant check: fail closed before commit。

性能目标必须通过 benchmark 仓库与固定硬件说明发布，不能写进 README 当既成事实。

## 20. Failure semantics

统一错误类别：

```text
INVALID_INPUT
PRECONDITION_FAILED
INVARIANT_VIOLATION
NOT_FOUND
CONFLICT
RATE_LIMITED
AUTH_DENIED_SIMULATED
TIMEOUT_BEFORE_EFFECT
TIMEOUT_AFTER_EFFECT
PARTIAL_EFFECT
UNMODELED_BEHAVIOR
SPEC_DRIFT
RESOURCE_LIMIT
INTERNAL_TWIN_ERROR
```

对 Agent-facing output，可以映射成 upstream-like error envelope；内部 audit 必须保留 canonical class。

## 21. Testing strategy

### Layer 0 — Pure deterministic unit tests

DSL parser、expression evaluator、canonicalization、PRNG、clock、hashing。

### Layer 1 — Transition/property tests

- preconditions
- postconditions
- invariant preservation
- idempotency
- rollback on failure
- snapshot immutability

Property-based/fuzz testing SHOULD 用于输入 schema 与 transition expressions。

### Layer 2 — MCP conformance

使用官方 conformance suite / SDK tests 验证 target protocol subset。

### Layer 3 — Differential tests against upstream

对安全、可重置的 fixture account：

```text
same initial fixture
same call
real system result/state projection
vs
Twin result/state projection
```

对比只覆盖 declared observable fields，不比较隐藏实现细节。

### Layer 4 — Agent behavioral tests

同一 snapshot 下分别让 OpenAI/Claude/其他 agent 执行 scenario。验证 terminal state，不要求 trajectory identical。

### Layer 5 — Fault tests

每个故障类别必须有 deterministic seed reproduction。

## 22. Release and compatibility policy

### TwinSpec versioning

- `v1alpha1`: schema 会变化，不保证跨 minor 完全兼容。
- 首次 beta 前实现 `statetwin migrate`。
- Canonical export format 必须独立于 internal DB schema。

### Runtime compatibility

Snapshot metadata 包含 runtime schema version。新 runtime：

- MUST refuse unknown newer schema。
- SHOULD migrate supported older schema。
- MUST preserve old export digest semantics or bump export format version。

### Upstream compatibility

Tool surface drift 不自动升级 TwinSpec。用户必须运行：

```text
statetwin inspect --upstream ...
statetwin diff-surface
statetwin revalidate
```

## 24. Proposed implementation stack

- **Language:** Go。
- **MCP:** official `modelcontextprotocol/go-sdk` Tier-1 line supporting MCP 2026-07-28。
- **Storage:** SQLite first；通过 storage interface 避免 API 锁死。
- **Spec:** YAML authoring, alpha canonical JSON hashing（ADR-0005）。
- **CLI:** single binary `statetwin`。
- **Expression engine:** bounded `cel-go` environment with a per-expression cost limit（ADR-0003）。
- **Telemetry:** OpenTelemetry optional integration。

选择 Go 的工程理由：单二进制部署、适合 proxy/runtime、并发与 server tooling 成熟，同时有官方 MCP Tier-1 SDK。不是因为 Go 与 AGI 有任何特殊关系。

## 25. CLI contract (proposed)

```text
statetwin inspect --upstream https://...

```

最终 CLI 名称在实现前冻结，避免早期兼容负担。

## 29. Key open questions

1. **Resolved for the development preview:** TwinSpec uses bounded CEL；见 ADR-0003。完整静态读写集分析仍是后续问题。
2. Tool output template 是否只允许 field mapping，还是支持 bounded functions？
3. **Resolved for the development preview:** SQLite + full logical JSON snapshots；见 ADR-0004。COW/delta/GC 必须在 benchmark 后另开 ADR。
4. Recorder 如何对 streaming/large blob 做脱敏和截断？
5. 是否需要保留 upstream 原始 server name/instructions，还是 namespaced overlay？
6. L2 的 differential validation coverage 如何量化，避免虚假的“high fidelity”标签？
7. 对 remote hosted twin 的 auth 是否直接复用 MCP OAuth 还是只支持 reverse proxy auth？

其余问题不会阻塞当前 development preview，但在对应能力进入 release scope 前必须分别落 ADR。

## 30. Product success metrics

不要用 stars 作为唯一目标。更有价值的指标：

- 有多少真实 MCP server/项目维护 TwinSpec。
- 每个 Twin 的 differential validation coverage。
- CI 中避免了多少 live external calls。
- 同一 agent eval 的 rerun variance 中，有多少环境噪声被消除。
- model/tool upgrade 前后发现的 regression 数量。
- 外部贡献者新增的 domain adapters/scenarios。
- issue/PR/release 活跃度与下游使用证据。

这也更符合一个基础设施 OSS 逐渐形成 ecosystem importance 的路径。

## 31. What we can and cannot guarantee

### We can engineer toward

- hermetic isolation
- deterministic simulated state transitions
- repeatable snapshots/forks
- explicit modeled semantics
- protocol-compatible tool surfaces
- reproducible fault schedules
- auditable state diffs

### We cannot honestly guarantee

- twin automatically matches every undocumented upstream rule
- one run predicts real production perfectly
- different LLM providers behave identically
- simulation eliminates all agent failures
- future MCP/client versions never require adapters
- project will “definitely become popular”

项目的可信度来自把这些边界写清楚，而不是把未知当成功能。
