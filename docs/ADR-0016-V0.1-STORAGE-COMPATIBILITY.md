# ADR-0016: v0.1 Local Storage Compatibility Profile

- **Status:** Accepted
- **Date:** 2026-08-24
- **Decision owners:** repository maintainers
- **Amends:** ADR-0007 and the accepted subset of SPEC-0012
- **Release profile:** RFC-0002 local hermetic L1 runtime

## Context

The runtime already identifies SQLite files, refuses foreign and future
versions, and migrates early development schemas. That was insufficient release
evidence because there was no schema-v3 fixture, no fixture tied to the public
alpha tag, and no process-exit test inside the migration transaction.

Disk-full testing, network-filesystem SQLite, online backup, high availability,
and multi-host writers are different operational profiles. Requiring them for a
single-host local v0.1 would either create unsupported claims or delay a bounded
runtime behind features it does not expose.

## Decision

Stable v0.1 supports one process, one local SQLite file, serialized writes, and
storage schema v4. Its compatibility evidence MUST include:

1. application identity and current-version tests;
2. refusal of a foreign non-zero application ID and any future schema version;
3. forward migration fixtures for supported historical schemas v1, v2, and v3;
4. a synthetic fixture tied to every public tag that used a database schema,
   beginning with `v0.1.0-alpha.1` at commit
   `8eba96819d865a0616b425751a9ca2cb2d780c54` and schema v4;
5. preservation of branch, snapshot, audit, control-audit, and fault data where
   those tables existed; and
6. subprocess kill-points after schema mutation and after metadata mutation but
   before commit, followed by a successful reopen and `PRAGMA integrity_check`.

Migration hooks remain unexported test instrumentation. `Open` does not expose
an application-controlled partial-migration mode.

## Explicit exclusions

The v0.1 storage claim does not include:

- shared or network-filesystem databases;
- multiple runtime processes writing the same file;
- disk-full or host-filesystem durability guarantees;
- online backup/restore or point-in-time recovery;
- high availability, replication, or disaster recovery; or
- compatibility with untagged private development databases beyond the tested
  historical schemas.

These exclusions must remain visible in README and release notes. They are not
implemented capabilities.

## Consequences

- RFC-0002's bounded storage-compatibility gate may be marked passing only when
  all tests above pass in CI.
- A future schema bump requires a new forward fixture and the most recent tagged
  schema fixture before release.
- Adding any excluded deployment profile requires a separate ADR, failure-mode
  review, and executable recovery evidence.
